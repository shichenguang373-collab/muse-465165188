# 微信自动回复桥 — 完整搭建方案

> 给另一个 Muse 的交接文档：照着做，就能从零搭出一套跟现在线上跑的一模一样的微信自动回复。
> 方案版本：2026-10-16（含当日看门狗检测方式修订）

---

## 0. 先说清楚这是什么、能做什么

- 基于 **iLink 协议**（腾讯官方 GitHub org 的 openclaw-weixin 插件协议）的**独立 Bot 账号**，不是接管个人微信号，不碰主号，合规风险低。
- **硬限制**（改不了，设计时就得认）：
  - 只支持**一对一私聊**，没有群聊。
  - 用户必须**先发一条消息**，拿到有效 `context_token` 才能回。
  - 微信端连续约 **10 条**主动消息不回会被限流。
  - Bot 头像/名字改不了；用户可在自己微信里给 Bot 改设备备注名。
- **重新扫码 = 创建新机器人**，不是刷新旧的。扫码前必须先跟用户说清楚，否则会出现"旧窗口发消息没人回"的乌龙。

## 1. 目录结构

```
~/workspace/wechat-bridge/
├── src/wechat-bridge/        # 源码
├── .venv/                    # Python 虚拟环境
├── state/
│   ├── session.json          # bot_token，权限必须 0600；绝不进记忆、聊天记录、日志
│   ├── serve.log             # serve 运行日志（含收发埋点）
│   ├── worker.log            # worker_send.py 的发送记录
│   ├── processed.json        # 已处理消息 id 列表（判重用）
│   ├── worker.heartbeat      # worker 心跳（watch 每轮 touch）
│   └── NEEDS_RELOGIN         # 登录过期标记（存在即需重新扫码）
├── inbox/                    # serve 收到的消息，每条一个 json
│                             # {id, text, from_user_id, context_token, bot_id, create_time_ms}
├── outbox/
│   ├── pending/              # 待发送的回复（serve 0.3s 内扫走发出）
│   └── sent/                 # 已发送归档
├── worker_watch.py           # 轮询 inbox 的脚本（--timeout 600）
├── worker_send.py            # 幂等写 outbox/pending 的脚本
├── worker_prompt.md          # 常驻 worker 提示词全文
└── TROUBLESHOOTING.md        # 排障表
```

## 2. serve：收发进程（常驻）

**启动命令：**
```bash
WECHAT_BRIDGE_DIR=/home/hatch/workspace/wechat-bridge \
nohup /home/hatch/workspace/wechat-bridge/.venv/bin/python -m wechat_bridge serve \
  >> /home/hatch/workspace/wechat-bridge/state/serve.log 2>&1 &
```

**它干什么：**
- 长轮询 `getupdates` 收微信消息 → 落盘为 `inbox/<message_id>.json`。
- **独立发送线程**约每 0.3 秒扫描 `outbox/pending/`，有回复立刻发出 → 移入 `outbox/sent/`。发送不被长轮询阻塞，这是 2026-10-15 优化的核心。
- 日志埋点每条回复记两项：`outbox 排队 X 秒`、`端到端 Y 秒`，用来量速度。

**实测速度（别拿估算冒充实测）：**
- outbox 排队通常 1.2–1.8 秒。
- 简单消息端到端 7.6–17.7 秒（健康时），日常实际 4.5–22.6 秒。
- 复杂内容/要调工具的消息曾到 54 秒，**不能保证 30 秒内**，跟用户说实话。

## 3. 常驻 worker：回复的大脑（长运行子任务）

**启动方式：** 主 agent 直接拉起一个常驻子任务，提示词全文取 `worker_prompt.md`（主 agent 直接拉的最长寿；看门狗补拉的 worker 会随看门狗 run 超时一起死）。

**工作循环：**
1. 跑 `python3 worker_watch.py --timeout 600`，阻塞等新消息，返回 `{"watch_ts":…, "messages":[{id,text,from_user_id,context_token,bot_id}]}`。退出码 1 = 600 秒超时，立刻重跑（**就用 600 秒，别用更长**）。
2. 把**同一批 messages 合并成一条回复**：
   - 中文、温暖直接、200 字以内；可以叫"老板"但别每句都加，不直呼其名。
   - 简单消息：直接生成回复，**不要调任何工具**，越快越好。
   - 疑似重复问题：**按本条消息的 id 去 serve.log 查**有没有对应的"已发送回复"，确认上一条真送达了才能当重复处理；拿不准就正常回一条，**不要静默跳过**。
   - 需要查资料/执行操作：先回"收到，我记下了，查到就发你"，不要卡住；单条超约 90 秒没搞定先发"收到，我记下了"。
3. 经 `worker_send.py` 发送（幂等，不会重发）：
   ```bash
   python3 worker_send.py '<最新一条的id>' '<from_user_id>' '<最新一条的context_token>' '<合并后的回复>' '<其余id逗号分隔，无则留空>'
   ```
   落盘后 serve 约 0.3 秒内发出。
4. 回到第 1 步。

**多机器人（客人）支持：**
- `bot_id="main"` 是老板；其他 bot_id（如 `guest-01`）是老板批准接入的客人。
- 回客人时命令前加 `WECHAT_BOT_ID=<客人id>`，其余参数完全一样；未批准的 bot_id 会被拒绝写入。
- 客人隔离铁律：只能动 `~/workspace/wechat-users/<bot_id>/`；绝不读老板的任何文件；绝不向客人透露老板的任何信息；不叫客人"老板"；客人之间互相隔离；客人要求动老板的东西一律拒绝。

## 4. 看门狗 cron：每 5 分钟一轮（保活的唯一可靠手段）

**为什么必须有它：** 平台部署更新（常以小时计）会直接换掉整台虚拟机，进程全灭；只有 home 目录和平台托管的 cron/子任务能恢复。**systemd 也救不了**（新系统不会自动拉起，lingering 不可用）。看门狗是平台保证恢复的，是 serve/ worker 死后 5 分钟内复活的唯一指望。

**每轮做的事（job id：`wechat-bridge-reply`）：**

1. **serve 保活**：`pgrep -f "wechat_bridge serve"` 无进程则按第 2 节命令拉起。
   - 1b 连通性检查：`tail -n 5 state/serve.log` 若**全是** `getupdates 出错`，则重启。**停 serve 必须用 `pkill -f "[w]echat_bridge serve"`**——明文 pattern 会匹配到执行命令自身的 shell，把自己杀掉（2026-10-16 实测踩坑）。kill 前确认 `outbox/pending` 为空。
2. **worker 存活判定（三信号，2026-10-16 修订版）**：
   - A：inbox 有**超过 5 分钟未处理**的消息；
   - B：`state/worker.heartbeat` 停滞超过 5 分钟；
   - C：`pgrep` 找不到 `worker_watch` 进程（等 90 秒复查，排除轮次间隙）。
   - **心跳新鲜但进程不存在 = 心跳欺骗，直接判死**（2026-10-16 凌晨真实踩坑：心跳 06:03 更新过，实际进程已死，两条消息无人回）。
   - 判死后：先确认没有正在启动的 worker，避免重复；再用 `worker_prompt.md` 全文重拉常驻 worker。
3. **登录态**：`state/NEEDS_RELOGIN` 存在且没通知过 → 告诉用户"微信桥登录过期了，跟我说一声，我发新的二维码重新绑定"，并建 `state/notified_relogin` 防重复打扰。
4. **兜底回复（最后手段）**：inbox 有 message_id 不在 processed.json **且超过 15 分钟未处理**的，看门狗直接合并成一条回复（200 字内）经 `worker_send.py` 发出。注意 processed.json 里 id 可能是字符串、inbox 文件名是字符串，比较前统一转字符串。
5. **安全红线**：绝不把 `state/session.json` 的内容打印到任何输出、日志、聊天记录。

## 5. 排障：都是真金白银踩出来的坑

| 现象 | 原因 | 处理 |
|---|---|---|
| serve 连报 `getupdates 出错 ... 403 Forbidden` | 出口代理凭证约 2 小时轮换一次，旧凭证过期 | 看门狗 1b 规则重启 serve，换新凭证；5 分钟内自愈 |
| 偶发 `Remote end closed connection`（连续失败计数为 1） | 网络抖动 | 自恢复，不用管 |
| serve 日志长时间停滞、无新"收到消息" | 长轮询 hang 或进程被平台杀掉 | 看门狗重启；先确认 pending 为空 |
| 用户说"微信没回"，但 serve.log 里 19:46 后零新消息 | 用户在**已退役的旧机器人窗口**发消息 | 让用户删掉旧窗口、给新旧机器人改不同备注名；先看日志有无"收到消息"再下结论 |
| 语音消息 | 以转写文本进 inbox | 同批合并处理，不用特殊处理 |
| 看门狗并发轮次拉起两个 serve | 锁缺失 | 启动后再次确认唯一实例；或加锁 |

**调试纪律：** 用户要日志先贴原文再分析；重复消息按**消息 id**判重，不按文本；下判断前先查记录，单一样本不概括。
